# ADR 0039 — Gateway interposition and the zone-transfer-capable session model

**Status**: Accepted (2026-08-20)

## Context

[ADR 0016](0016-server-modular-monolith.md) puts a thin gateway in front of the
shards. [ADR 0033](0033-m2-module-topology-gateway-deviation.md) allowed M2 to
connect clients directly to a shard, but billed the missing gateway to "M3, or
the first time a second shard or a second zone exists". M3 pays that bill before
a second zone makes the direct path harder to remove.

The current `server/internal/session` package mixes two lifetimes. A client
connection performs the public hello, presents a single-use ticket, and holds a
play lock. The same handler loads a character, creates a zone entity, dispatches
gameplay commands, sends snapshots, and saves the character on teardown. A zone
transfer cannot preserve the first lifetime while replacing the second because
the code represents both as one `session.Server.handle` call.

The split must preserve two boundaries from ADR 0033. `internal/session` remains
the only shard package that dispatches wire messages into simulation modules,
and no simulation module learns about a connection, route, credential, or
ticket. The implementation is also constrained by the current source, not an
idealized package diagram: admission and zone work share `handshake.go`, while
play-lock renewal shares a function with periodic character saves in
`character.go`.

M3 serves one zone on one shard. The model below still names a gateway session
and a replaceable zone attachment separately, so adding a route does not require
another session rewrite. Cut-ladder rung 5 may make an attempted transfer return
a typed refusal. It does not restore direct client-to-shard admission or combine
the two lifetimes again.

## Decision

### 1. One gateway session, zero or one shard attachments

The public client connects only to `cmd/gateway`. The gateway terminates public
QUIC and TLS, performs `ClientHello` and `ServerHello`, enforces the protocol and
pack checks, reads `EnterZoneRequest`, redeems its ticket, and holds the auth play
lock until the public session ends. The ticket never crosses the gateway-to-shard
boundary.

The gateway owns this state:

```
GatewaySession
  session_id        UUIDv7, generated by the gateway
  state             Connected | Versioned | Authenticated | Attaching |
                    InZone | Transferring | Draining | Closed
  account_id        UUID
  character_id      UUID
  character_name    string
  chargen_option_id string
  attachment_epoch uint64
  current_zone_id   string
  current_shard_id  string
  client_connection transport.Connection
  shard_attachment  optional private connection
```

`session_id` identifies one public connection. `attachment_epoch` starts at one
and increases before every attach or transfer attempt. The pair is the
idempotency key on the private protocol. The gateway permits at most one active
attachment for a session and keeps the one-session-per-character registry. It
also renews and releases the play lock. The lock holder is the gateway instance,
not a shard, so a transfer does not release and reacquire it.

The shard receives an asserted identity over an authenticated private channel.
It owns this shorter-lived state:

```
ZoneAttachment
  session_id        UUID
  attachment_epoch uint64
  asserted_identity account_id, character_id, character_name,
                    chargen_option_id
  state             Asserted | CharacterBound | InZone | Detaching | Detached
  zone_id           string
  entity_id         uint64
```

An attachment runs character load, `JoinAt`, module admission, command dispatch,
replication, checkpoints, and `Zone.Leave`. An `entity_id` belongs to one
attachment and may change after transfer or reconnect. The shard retains a
character-keyed attachment registry as a second line of defence against a buggy
or restarted gateway creating two entities. This registry does not redeem
credentials or own the play lock.

The gateway forwards complete protobuf envelopes. It does not interpret combat,
loot, quest, device, or spell payloads. Reliable client commands and reliable
server events keep their order. Movement is newest-wins on the gateway-to-shard
hop. Snapshots are newest-wins on the shard-to-gateway hop and again at the
public edge. A bounded reliable-event queue disconnects a client that stops
reading rather than dropping a committed event. These separate queues pay ADR
0033's warning that backpressure must be decided independently at both hops.

The gateway advertises one configured public `pack_id` during the hello. Every
enabled route must declare the same `pack_id`; the gateway refuses to start if a
route disagrees. This is necessary because the hello precedes the zone request.
It also prevents a successful hello followed by routing to a shard with different
content.

private attachment instead of a public client connection.

New gateway relay, routing, trust, and transfer files belong under
`internal/gateway`. New private control protobufs live outside the client
`sarnaut/v1` tree, as the auth service protobufs already do. The client must not
receive or compile the private identity assertion.

### 3. M3 authenticates the private channel with a shared secret

The shard binds a separate internal listener to a private address. The public
listener is removed after the delivery guard in section 7 passes. Network
placement is defence in depth, not the identity check.

M3 uses TLS 1.3 plus a versioned 256-bit shared secret held in runtime secret
configuration. The secret is never committed or logged. The shard presents an
internal server certificate that the gateway validates against a pinned internal
CA. After TLS, the peers run a challenge-response before any identity assertion:

1. The shard sends a protocol magic, version, shard id, key id, and 32 random
   bytes.
2. The gateway sends its instance id, 32 random bytes, and HMAC-SHA-256 over the
   protocol label, both ids, both nonces, and the negotiated version.
3. The shard verifies the proof in constant time and returns the same transcript
   under a different direction label.
4. Only after the gateway verifies that response may it send `AttachRequest`.

The nonces bind proofs to one TLS connection and prevent replay. A distinct label
in each direction prevents reflecting one proof as the other. The private
protocol begins with a fixed magic value, so a direct public client gets a typed
private-protocol refusal or a timeout before it can present a client message. A
shard accepts `AssertedIdentity` only on a channel that completed this exchange.
The attach request carries `session_id`, `attachment_epoch`, `zone_id`, and the
four identity fields. It carries no ticket, account session token, or auth schema
credential.

A shared secret is the M3 choice because there is one gateway, one shard, and one
route. It gives the new boundary an authenticated, replay-resistant protocol
without introducing certificate issuance and rotation machinery in the tutorial
milestone. The symmetric secret has a small blast radius only while that topology
is true.

M4 replaces the shared secret and HMAC exchange with mutual TLS. Gateways and
shards receive distinct short-lived workload certificates, and shard policy
authorizes the gateway identity from the client certificate. The server-only
private messages and asserted identity remain unchanged. M4 removes the shared
secret configuration, overlap key ids, and proof code after both certificate
identities are deployed.

### 4. The gateway owns the zone routing table

The gateway loads a closed routing table at startup:

```
zone_id -> { shard_id, private_address, pack_id, enabled }
```

Zone ids are unique. Empty destinations, duplicate zone ids, disabled requested
routes, and route pack ids that differ from the public pack id are startup or
request failures, never fallbacks to a direct shard address. M3 commits exactly
one enabled entry for `InstLeague1`. Configuration may contain the table, but no
client-supplied host or shard id participates in lookup.

Existing attachments stay pinned to the shard selected for their current
epoch. A table change affects a new attach or the next transfer. If the private
connection fails while the public gateway session survives, the gateway resolves
the current zone again and attempts a new attachment epoch with the identity it
already holds. If it cannot recover within the bounded attach timeout, it sends a
typed `ReconnectRequired` error and closes the public connection.

A lost public connection is not resumed. The client returns to auth for a new
single-use ticket, reconnects to the gateway address, repeats the hello, and
enters the character's durably saved zone. It never retries the burned ticket and
never falls back to the shard address. The new attachment receives a new
`session_id` and `entity_id`.

### 5. Zone transfer is a replaceable attachment handshake

A normal transfer keeps the public client connection and play lock. It replaces
only the shard attachment. The reliable private control channel runs this
idempotent handshake:

1. The source shard sends `TransferRequested{session_id, current_epoch,
   destination_zone_id}`. The gateway validates the current epoch and resolves
   the destination route.
2. The gateway increments the epoch and sends `PrepareDetach` to the source.
   The shard stops dispatching new gameplay commands, takes one character
   snapshot under the zone lock, and persists transfer checkpoint S4
   synchronously. The entity remains present but frozen. The shard replies
   `DetachPrepared{save_seq}`.
3. The gateway sends `CommitDetach`. The source unsubscribes sinks, releases
   module bindings, calls `Zone.Leave`, and replies `Detached{save_seq}`. Only
   after this acknowledgement may the gateway attach the destination, so two
   zones never contain the character at once.
4. The gateway opens and authenticates the destination channel, then sends
   `AttachRequest` with the asserted identity, new epoch, destination zone, and
   `minimum_save_seq`. The destination loads at least that save sequence, joins
   the zone, takes S0, and replies `Attached` with the new entity id and spawn.
5. The gateway sends a reliable zone-changed event to the client. The client
   clears old entity and interest state and keeps using the same public
   connection.

Every control request and reply is keyed by `(session_id, attachment_epoch)`.
The shard records the last terminal result long enough for a retry to return the
same result rather than repeat `JoinAt` or `Zone.Leave`. If the gateway disappears
before `CommitDetach`, the source aborts its prepared state after a timeout and
unfreezes the attachment. If the destination attach fails after `Detached`, the
gateway performs a new attachment back to the source zone from S4. During that
recovery there is no active entity, which is preferable to two active entities.

If cut-ladder rung 5 fires, step 1 receives `TransferRefused{UNAVAILABLE}` before
`PrepareDetach`. The current attachment continues. The gateway interposition,
asserted identity, routing table, session split, epochs, and private control
envelope still ship.

### 6. Admission and dependency cleanup

Ticket redemption and play-lock renew and release happen at the gateway. Auth's
session-revocation subscription also terminates there because the gateway owns
the authenticated connection. The shard has no NATS client for admission and no
generated `sarnaut.auth.v1` dependency in `internal/session`.

The dated NATS exemption for `internal/session` is removed from `.golangci.yml`
in the gateway implementation PR once all of the following are true: the gateway
redeems tickets, owns play-lock renewal and release, handles revocation, and
`rg 'nats-io|sarnaut/auth/v1|ticket' internal/session` finds no admission or
credential dependency. Removing only the ticket call while leaving lock traffic
on the shard does not meet the condition.

The shard-side depguard row may continue to let `internal/session` import
`internal/transport`, since it owns the private attachment. No simulation module
may import `internal/transport` or refer to a ticket. Depguard enforces the import
rule, and an `rg` check over the eight module directories enforces the credential
rule.

### 7. Delivery and containment gates

Session-dispatch verb additions freeze once the last verb-adding task merges.
The coordinator confirms that devices and spells have landed and no other verb
change is in flight before the implementation splits `reader.go`. New transfer
control messages are not gameplay verbs and use the private control envelope.

The direct-to-shard path remains behind an explicit configuration toggle until
`scripts/m3-tutorial-driver` is green through both the direct path and the gateway
path. The direct path is deleted in the same PR that records that proof. A failure
on the gateway path is not grounds to keep an undocumented fallback or to move
the exit gate.

ADR 0033's containment condition becomes the implementation acceptance, stated
without qualification: **`git diff --stat` must show ZERO changes across the
eight simulation modules (world, interest, combat, loot, inventory, quests, chat,
charstore).** The command compares the implementation branch with its merge base
and names all eight directories. A needed change in any one of them requires an
ADR amendment before implementation continues.

The same implementation must show that no simulation module imports
`internal/transport` or refers to a ticket. Routing, private trust, relay policy,
and transfer coordination belong to `internal/gateway`, `internal/session`,
`internal/transport`, private protobufs, and process wiring. They do not belong
to a simulation module.

## Consequences

- A public certificate rotation or connection policy change restarts the gateway,
  not a process holding zone state. Shards expose only an authenticated private
  listener.
- Ticket redemption is written once at the edge. Shards consume asserted UUIDs
  and character metadata but never credentials.
- One player now consumes a public connection and a private attachment
  connection. M3 accepts that cost. Multiplexing private attachments may follow
  profiling, but it must preserve ordering, per-session budgets, and the transfer
  epoch.
- A normal zone transfer pauses command dispatch around a durable checkpoint.
  It keeps the public connection and play lock, creates a new entity id, and never
  places the character in two zones at once.
- The M2 session spec remains an accurate record of the direct topology it
  specified, but its statements that the shard redeems the ticket and that zone
  transfer is open are superseded by this ADR. A later spec update should describe
  gateway sessions and zone attachments using the terms fixed here.
- Mutual TLS is deferred, not optional. Adding more gateways or shards before the
  M4 credential upgrade expands the shared-secret blast radius and requires an
  explicit review of this decision.
